## Selection and dependency closure

The selection retains the complete six-document D1 dependency set (`world`, `panel`, `messages`, `scripts`, `sound`, `service`) and its exact file/source hashes. It adds the original METIS Body offset 60 (`body-15`), TOLOSA offset 100 (`body-25`), their island descriptors and groups 3 and 23. The manifest enumerates all 39 original nonzero exterior placements, all 512 ground workspace bindings, 18 selected structure slots, the actual scales/palettes/details, Selected Pieces, Drawn Records, orientations, road joins and street-furniture entries. All records come from the [validated Catalogue](../dion-catalogue-contract.md); every selected identity's record hash, file hash, forms and half-open source-range hashes are retained.

The bounded drawing set intentionally covers the two complete 16×16 workspaces, including empty/fallback cells. This avoids inventing a scene-dependent cutoff for free exterior movement and covers the departure/descent perspectives. It is not a claim that the flight visits every cell, that a neighbouring building interior is playable, or that the fixed drawn-list residents belong to the currently occupied cell. The original draws the **bound occupied-cell structure/ground**, then separately selected residents/coast/sky; it does not draw an arbitrary ring of neighbouring Catalogue buildings. The [encountered-cell derivation and original-frame checks](mercenary-iii-tourcraft-views.md) delimit the actual flight separately.

The Catalogue selection contains **79 Geometry Identities and 109 stored forms/transforms**. The recovered embedded DAMOCLES sky-tail record additionally receives presentation identity `sky-tail-0502c0`, form `base`, pinned to `$502C0..$502F2` in the gameplay opening: **80 total geometry identities and 110 forms/transforms**. It is an explicit title-local sky dependency outside the Catalogue's 529-identity ledger, with no invented Catalogue record or additional destination. These counts are calculated from explicit references, not the Catalogue's complete per-Body geometry list (which also includes upper Floors and unrelated driver heads). Geometry selection follows:

1. Every selected placement's Floor 0 binding → its exact scaled structure and unscaled detail, palette, lettering and association/region/attachment data. An alias is resolved as a binding; it never becomes a new geometry name. D1's existing structure variants are retained separately.
2. Every ground cell → both its Selected Piece and actual Drawn Record, the recorded transform, road joins and every template's model-table entry → that entry's Geometry Identity/forms. Empty geometry remains an evidenced empty record, not a missing dependency.
3. The D1 model entries and residents → their existing model/header/view forms. Resident 13 additionally requires TOURCRAFT `model-03005c` at `$3005C`: `form=default`, `form=view-1` and `state=passenger;form=default`. The used pilot is entry 279, `model-0381de`, with profile entry 280, `model-038282`. Other resident-13 service heads and other flights are excluded.
4. TOLOSA surface resident 174 and passive actors 56–58 → their initial/used model bindings; passive entry 320 is `model-03108a`. The Catalogue indexes that geometry by slots 56–58, so entry 320 is an evidenced runtime binding, not a name parsed from its ID. Hostile entry 321/model `$31140` is excluded by [R6's nonfiring/default-programme proof](mercenary-iii-tourcraft-campaign.md#passive-encounter-programme-and-phase-ownership).
5. The two island placements → recovered `island-06330a`, their separate original descriptors/origins/land colours and recovered core/outer boxes; both have no coastline vertices, sea boxes or edges. System sky drawing/arrival scan has its own roster dependency; a sky Body never gains surface/group content or becomes a Destination by being drawn.
6. Presentation → the selected source fonts/glyphs, token bindings/live-token rules, colour/rotation/projection tables, sky/Body records, PSG programmes and animation sequences documented in the presentation handoff. The manifest explicitly selects six vector fonts (0, 1, 2, 5, 6, 7), their 385 recovered glyph records, 13 full 64-entry night/day palettes and ten lettering tokens. Glyph `2:01` retains the Catalogue's recovered malformed-ground diagnostic record; no invented character repairs it. Token `$9E` is included for the registered `$800D` route-buffer writer even when no selected face directly requests it. Live and placement tokens retain their writers/bindings rather than their Catalogue opening strings. Campaign and flight dialogue request their original text dependencies and message font/tone rules.

The manifest's `legacyModels`, `placements`, `structures`, `surfaceCells`, `residents`, `services` and `geometry` are exhaustive reference lists for that static selection. `catalogueRecordSha256` hashes the **whole unchanged recovery record**, excluding its own hash field using sorted compact ASCII-escaped JSON. `selectedVariantsSha256` independently hashes the selected variant dictionary by the same rule. `sourceRecordSha256` on a binding hashes its unchanged Catalogue source record, before specification annotations. A consumer must look up records by explicit IDs/fields, never split an app ID to invent an original reference. The manifest's legacy D1 source is a historical immutable dependency pin, not an alias for the new initial capture.

## Version 1 export/admission contract for I3

The version-1 specification is not admitted by today's six-document loader. I3 introduces a separate strict promotion schema and export/admission path, preserving existing Catalogue source checks. In particular:

- Pin all input file bytes and source ranges; validate Catalogue record content hashes and exact selected forms before extracting a subset. Retain original header transforms, stateful rules and binding provenance. The specification records `recovered`, `derived` or `authored` disposition through record fields and its section-wide `fieldDispositions`/`dispositionRules`; pointer resolution, scale application, canonical subset selection and hashing are derived, while 50 Hz/eleven-tick cadence and browser colour conversion retain their accepted authored status. None is a new invented world datum.
- Whole Catalogue/ledger/render-support file hashes in this research specification are **input audit pins**, not fields copied wholesale into the served playable manifest. Export stable actual program/capture/source-range and selected record/form identities instead. Rebuilding unrelated Catalogue coverage or an unused palette/glyph must not change selected playable bytes through a changing whole-export hash. A genuinely changed selected record or capture retains its actual identity and can change play identity.
- Export independent playable documents. A runtime reads only playable paths and never consults `payload/dion/catalogue/`. Do not weaken its current single-source comparison: explicitly admit immutable record pins separately from the **one** mutable initial-state source under the new schema. Catalogue-only export changes remain irrelevant to play.
- Resolve every placement/body/group/cell/slot/Floor/geometry/form/palette/glyph/token/template, used service/stream/action, script/call/branch/message, programme/trajectory and presentation dependency before enabling play or restoration. Check excluded alternative targets against the reachable-state proof instead of dropping arbitrary unresolved branches. Required unrecovered references block export.
- The exporter emits an ordered `playableDocuments` list: six retained/expanded top-level playable documents in the existing `DION_DOCUMENTS` order, then the independent promotion metadata, selected geometry files in bytewise ID order, and title-local presentation support/programme documents in bytewise path order. The exact paths/schema and order are part of the served manifest. Refuse duplicates, unlisted dependencies and path traversal.
- Define `contentSha256` over the UTF-8 path and exact served file bytes for **every** listed document with explicit length delimiters; use one documented encoding and golden fixture in I3. Include the manifest itself with its derived `contentSha256` field omitted (or keep the final digest outside the hashed document); never hash a self-referential digest. The served semantic manifest is independent of Catalogue export timestamps or unselected records. Admit/verify every dependency even if drawing later loads it lazily, before restoring a Gameplay Session. Altering any selected geometry, presentation rule, initial state or programme changes playable identity. Changes to an unselected Catalogue record do not.
- Reconcile the manifest against D1 coverage and every R6 boundary: pre-B/admission/start, same-frame space reentry, Body setup, contact, recorded L and resident transfer, plus late campaign override/expiry. The views report's complete reference and coverage checks distinguish original facts from raster/browser equivalence.

R8 still owns complete expanded snapshot fields and restored-future acceptance. ADR 0073 retires old prototype migration. Passing manifest/geometry compatibility does not establish snapshot completeness, prove a programme can be reconstructed, or authorize an unknown capture/content identity. I4 must validate first-frame, panel, sound and resumed future across the phase boundaries; no new Save schema is specified here.
