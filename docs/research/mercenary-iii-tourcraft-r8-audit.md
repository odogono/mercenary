## What R8 requires versus I4 implementation

#709 explicitly excludes runtime/codec implementation. Its browser criterion says to **specify** Save/Session Resume acceptance, and its migration criterion says to **specify deterministic initialization**. Therefore a playable schema-2 codec and production browser flight checks can remain I4 work. That boundary does not make an abstract canonical-selection permission a validated migration contract: R8 must document a deterministic reference rule and field-level construction, supported by recovered source/reachability facts and independently checked derivations. The issue goal is a validated contract, while D2 explicitly retains reconstruction proof. Preserve the old allowlist and execute retained old source/data, rather than changing its expected hash to accept unrelated current content. The newer history audit already demonstrates a pinned `git archive e4cba434` approach. [Migration audit implementation](../../research/mercenary-iii-st/scripts/taxi-migration-audit.ts), [history audit](../../research/mercenary-iii-st/scripts/taxi-history-audit.ts), [current content reader](../../web/src/dion/content.ts), [tracked-document helper](../../web/test/dion-documents.ts)

2. **The expanded fingerprint now exists.** Both persistence and migration reports still say it cannot be pinned before I3 exports it. I3 has supplied strict `TourcraftContent` admission and the exact served identity `d31490d7ba44a08949f71267884f1e290074acc5885fdfae747f7aeefcfdf611`, independently recalculated during this audit. This is expanded *content* admission, not expanded Gameplay Session or Save support. Keep this identity separate from both the historical old allowlist and current legacy content. [I3 identity contract](../dion-tourcraft-content-contract.md#admission-and-identity), [expanded loader/type/hash](../../web/src/dion/tourcraftContent.ts), [historical source tuple](mercenary-iii-tourcraft-taxi-migration.md#exact-allowlisted-source-identity)

3. **Refused Session Resume already has a shell protection guard.** `readDionResume()` does return a fresh session with a reason, but current `boot.ts` sets `protectResume`, suppresses advancement and all checkpoints, shows the menu and requires explicit New Game or successful Load to continue. Takeover resets the guard from the new read result. Describing the helper's fallback alone as proof of an automatic destructive boot rewrite omits the actual owner behavior. The existing source is protected in that path. [Dion resume reader](../../web/src/dion/resume.ts), [Dion boot guard/checkpoint/takeover/frame](../../web/src/dion/boot.ts)

4. **The shared write-failure path still removes the previous Session Resume.** `createSessionResumePersistence().checkpoint()` wraps encoding and writing in one `try`; on either failure its catch calls `removeStale()`, which removes the storage key, then disables persistence. The boot guard prevents refused-source flushing; it does not establish source preservation for every attempted successful-migration flush or encode failure. Future migration must explicitly preserve the source bytes before allowing this path. This is a source-level failure risk, not a production-browser failure reproduced here. [Shared resume persistence](../../web/src/shell/resume.ts), [migration transaction contract](mercenary-iii-tourcraft-persistence.md#snapshot-admission-storage-and-replacement-transaction)

5. **Slot replacement is partly transactional, but presentation is after commit.** Shared slot Load decodes first and never writes the slot. Dion boot creates a new candidate before assigning `session`, so validation failure preserves the active session. However it commits `session`/`snapshot`, resets audio and checkpoints Resume before calling `draw()`. The schema-2 contract promises presentation reconstruction before commit and failure preservation even during reconstruction. Current schema-1 callback is useful infrastructure, not proof of that stronger transaction. [Shared slot Load](../../web/src/shell/saves.ts), [Dion restore callback](../../web/src/dion/boot.ts), [transaction contract](mercenary-iii-tourcraft-persistence.md#snapshot-admission-storage-and-replacement-transaction)

6. **Source-validation and eligibility are different gates.** The reader admits bounded numeric fields and checks references when supplied `oldContent`, but accepts duplicate availability IDs, does not relate clock seconds to history, and projects away extra properties. It admits `remainder == 1/50`, while the schema-2 proposal uses a half-open interval. Current constructor also rescans the saved candidate. These observations require explicit migration-domain and normalization rules; they are not grounds to refuse ordinary late sources or claim every parsed state reachable. [Strict reader](../../web/src/dion/restore.ts), [constructor/capture](../../web/src/dion/session.ts), [source eligibility audit](mercenary-iii-tourcraft-taxi-migration.md#source-validator-and-eligibility-boundary)

7. **Historical conflict text and current decision are interleaved.** The migration report's later paragraph still says that replaying past campaign work/replacing cash and flags violates preservation and demands a D2 compatibility decision. Its opening follow-up correctly identifies that as the pre-revision conflict. Label the older section as historical, or express the current requirement as preservation of unrelated state plus canonical campaign reconstruction, so implementers do not infer a new approval gate. ADR 0068 already permits required late cash/script reconciliation and canonical history. [Historical conflict section](mercenary-iii-tourcraft-taxi-migration.md#historical-incompatibility-and-current-deterministic-construction-limits), [ADR 0068](../adr/0068-reconcile-known-taxi-saves-with-expanded-campaign-history.md)
